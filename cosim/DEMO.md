# Demo: Linux in QEMU talks to m0's RTL through co-simulation

Everything below was run on P2's laptop (Ubuntu 22.04, PetaLinux 2024.1) on 2026-11-21; the outputs and times are copied from that
run. Passwords are never written down: you type the guest password yourself, twice, at the prompts marked **[YOU]**.

## Talk track (about 45 seconds)

"We have no board, so we ran the hardware in simulation. The Verilog that Vitis HLS produced for our first model, m0, runs inside a
hardware simulator on this laptop. Next to it we boot our real Linux image in QEMU. A bridge connects the two, so when Linux
writes to the address `0x43C00000` it is really writing into the simulated chip's registers. First I read the control register
and the chip says it is idle. Then a script inside Linux sends 64 test records, one at a time, into the chip, starts it, waits for
it to finish and reads the score back. Every one of the 64 scores is identical to our Python reference. In this waveform you can
see one of them: the start signal, the chip busy for 284 clock cycles, then done. This is not real silicon: the clock here is
slowed to 10 microseconds so the boot is bearable, only model m0 was tried, and real timing on the FPGA is still untested."

## Commands, in order, with the expected output

Start the boot about 6 minutes before you need the audience; steps 5 to 7 are the live part (about 1.5 minutes).

**1. Clean start (laptop shell)**

```bash
export REPO=~/Desktop/OS-PROJECT
tmux kill-server 2>/dev/null; rm -rf /tmp/cosim && mkdir -p /tmp/cosim; rm -f $REPO/cosim/rtl/ids_cosim.vcd
df -h / | tail -1            # keep at least a few GB free
```

**2. QEMU in its own tmux session**

```bash
tmux new-session -d -s qemu -x 200 -y 50 'cd ~/plx/ids-os && source ~/petalinux/2024.1/settings.sh >/dev/null 2>&1; petalinux-boot qemu --kernel --dtb ~/Desktop/OS-PROJECT/cosim/system-cosim.dtb --qemu-args "-machine-path /tmp/cosim -icount 7 -sync-quantum 100000" 2>&1 | tee /tmp/qemu.log'
until [ -S "/tmp/cosim/qemu-rport-_cosim@0" ]; do sleep 1; done; ls /tmp/cosim
```

Expected: `ls` shows `qemu-rport-_cosim@0`. `/tmp/qemu.log` ends with
`qemu-system-aarch64: info: QEMU waiting for connection on: disconnected:unix:/tmp/cosim/qemu-rport-_cosim@0,server=on`.
(The line above it, `Failed to connect ... No such file or directory`, is normal.) QEMU now waits for SystemC and prints no boot text.

**3. The SystemC side in a second tmux session** (`IDS_COSIM_VCD_CLK=1` also records a short clock window for the waveform)

```bash
tmux new-session -d -s sysc -x 200 -y 50 'cd ~/Desktop/OS-PROJECT/cosim/sc && IDS_COSIM_VCD_CLK=1 ./run.sh unix:/tmp/cosim/qemu-rport-_cosim@0 100000 2>&1 | tee /tmp/sysc.log'
sleep 3; cat /tmp/sysc.log
```

Expected:
```
        SystemC 2.3.3-Accellera --- Mar 17 2022 13:55:26
        Copyright (c) 1996-2018 by all Contributors,
        ALL RIGHTS RESERVED
Info: (I702) default timescale unit used for tracing: 1 ps (ids_cosim.vcd)
connect to /tmp/cosim/qemu-rport-_cosim@0
```
QEMU starts booting as soon as this connects. There must be **no `DECODE ERROR` lines** at any time: `grep -c DECODE /tmp/sysc.log` prints `0`.
The VCD file (`cosim/rtl/ids_cosim.vcd`) is written while it runs; keep an eye on it: `ls -la $REPO/cosim/rtl/ids_cosim.vcd` (about 1.3 MB at the end).

**4. Wait for the login prompt, then log in [YOU]**

```bash
until tmux capture-pane -p -t qemu | grep -q 'login:'; do sleep 2; done; tmux capture-pane -p -t qemu | tail -3
tmux attach -t qemu          # log in as the guest user, then run:  sudo -v   (type the password), then detach with Ctrl-b d
```

Expected prompt: `xilinx-zc702-20241 login:`. Boot takes about 6 minutes (see timings). After login the prompt is `xilinx-zc702-20241:~$`.
`sudo -v` caches the sudo password so the commands below do not stop at a prompt.

**5. Paste the test script into the guest (laptop shell)** (the guest root is a RAM disk, so this is needed after every boot)

```bash
$REPO/cosim/linux/paste_to_guest.sh qemu
```

Expected: the laptop prints `laptop : 0c7978de768ab8349fcd9162e089be57b5ac6718527d0d7f057e4f7c25c562a5  .../cosim_test.py`, and the guest
console then shows
```
108 /tmp/cosim_test.py
0c7978de768ab8349fcd9162e089be57b5ac6718527d0d7f057e4f7c25c562a5  /tmp/cosim_test.py
```
(same hash on both sides, 108 lines). Takes about 45 seconds.

**6. Read the IP's control register (guest console)**

```sh
sudo devmem 0x43C00000 32
```

Expected: `0x00000004`. Bit 2 is ap_idle: the chip is alive and idle. (`0x00000081` would mean the IP was started by stray writes: see Troubleshooting.)

**7. Run all 64 canary records through the simulated hardware (guest console)**

```sh
cd /tmp && sudo python3 cosim_test.py --base 0x43C00000 --canary /opt/ids/pool-factory/canary.npz
```

Expected (takes about 46 seconds, mostly Python/NumPy start-up):
```
AP_CTRL = 0x00000004 (ap_idle bit2 set)
model m0.npz thr=1, 64 records
rec  0  got    -12/atk 0/id 0   expected    -12/atk 0   MATCH  (3 polls)
   ...   (records 1 to 62, one line each; every line must end in MATCH)
rec 63  got     16/atk 1/id 0   expected     16/atk 1   MATCH  (3 polls)
SUMMARY: 64 records, 64 match, 0 mismatch -> PASS
```
The poll count per record can vary from run to run (it was 2 or 3 in the runs we did); the scores must not. For a quick smoke test add `--limit 3`.
The guest's own `time` shows about 1m06s because its clock runs slow under `-icount 7`; quote the wall-clock numbers below.

**8. Shut down and make the small waveform (laptop)**

```bash
tmux send-keys -t qemu C-a x          # quits QEMU; ids_cosim then exits and closes the VCD
sleep 8; pgrep -a 'qemu-system|ids_cosim' || echo "both stopped"
python3 $REPO/cosim/demo/trim_vcd.py $REPO/cosim/rtl/ids_cosim.vcd /tmp/one_inference.vcd
gtkwave /tmp/one_inference.vcd &
```

Expected: `window starts at 2069.959 s of simulated time; ~4300 events kept` (the exact second differs between runs).
A committed copy of the trimmed waveform from the run below is `cosim/demo/one_inference.vcd` (84 KB), so GTKWave can be opened without re-running anything.

## The waveform: how to open it in GTKWave and what to look at

```bash
gtkwave $REPO/cosim/demo/one_inference.vcd &        # GTKWave 3.3.x; or the file you made in step 8
```

1. In the **SST tree** (left, top) click **SystemC**. In the signal list below it, select `ap_idle`, `ap_start`, `ap_done`, `clk`
   and press **Append** (or Insert).
2. In the tree expand **SystemC > top > signals**. Select these and **Append**:
   `awvalid`, `awready`, `awaddr`, `wvalid`, `wready`, `wdata`, `bvalid` (write channels),
   `arvalid`, `arready`, `araddr`, `rvalid`, `rready`, `rdata` (read channels).
3. In the signal pane select `awaddr`, `wdata`, `araddr`, `rdata`, right-click, **Data Format > Hexadecimal**.
4. **Time > Zoom > Zoom Full** shows everything (20 ms). To read the handshakes, zoom in around a transaction (about 200 us across);
   `clk` is the 10 us simulated clock, so each cycle is 10 us wide. The time axis starts at 0, 10 us before the first write.
   Click a rising edge to put the marker there; middle-click a second point and the time difference shows at the top.

What the waveform shows (times are from the committed file, measured from its start):

| Time | What you see |
|------|--------------|
| 10 us | First write: `awvalid` and `wvalid` high together, `awaddr = 0x40` (x word 0), `wdata` = four packed input bytes |
| 10 us to 12.6 ms | 16 writes to `0x40 .. 0x7C` (the 61-byte record, 4 bytes per word, about 0.73 ms apart because the guest is slow), one handshake each (`awready`/`wready` then `bvalid`) |
| 12.59 ms | 17th write: `awaddr = 0x00`, `wdata = 1` (AP_CTRL, ap_start) |
| 12.615 ms | **ap_start rises and ap_idle falls in the same cycle** |
| 12.615 to 15.455 ms | The chip is busy: `ap_idle = 0`, `ap_start = 1` for **284 clock cycles (2.84 ms)**; `rdata` of the polls reads `0x1` |
| 15.445 ms | **ap_done pulses for one cycle** |
| 15.455 ms | `ap_idle` goes back to 1 and `ap_start` falls |
| after that | Poll read returns `rdata = 0xE` (done, idle, ready); then reads of `0x10` (score `0xfffffff4` = -12, matches the expected value of record 0), `0x20` (attack 0), `0x30` (model id 0) |

Only the AXI signals, reset and the three `ap_*` signals are always recorded. The clock appears only inside a window of 20000 cycles
(0.2 s of simulated time, enough for about 8 inferences) that opens at the first write, because tracing the clock for the whole
boot would be several GB (about 1600 s of simulated time at 10 us per cycle). To change the window length:
`IDS_COSIM_VCD_CLK_CYCLES=40000`. Never trace the clock for the whole run.

`ap_idle`, `ap_start` and `ap_done` are internal to the RTL, not ports. `ids_cosim.cc` copies them out of the Verilated model:
`ap_idle` = `qmlp.ap_idle`, `ap_start` = `ctrl_s_axi.int_ap_start`, `ap_done` = `ap_CS_fsm[8]` (which is how `qmlp.v` defines `ap_done`).

## Troubleshooting (all of these happened while building this)

- **QEMU shows nothing for minutes and `ids_cosim` is at 100% CPU.** The simulated clock is too fast for QEMU's sync quantum
  (a 10 ns clock never boots). The program uses a 10 us clock (`QMLP_CLK_NS` in `ids_cosim.cc`). Do not change it.
- **`devmem 0x43C00000` returns `0x00000081`.** Something wrote to the IP during boot. In this image the AXI GPIO driver writes to
  `0x41200000`, and the interconnect sends unmapped addresses to target 0. The stub RAM in `ids_cosim.cc` prevents it. Check
  `grep DECODE /tmp/sysc.log`.
- **The VCD is growing by tens of MB per second.** Stop `ids_cosim` (`pkill -x ids_cosim`) and delete it. Only the windowed clock
  is safe; the demo's whole-model trace is not used.
- **`sudo` asks for the password again in step 6 or 7.** The cache expired; run `sudo -v` again in the guest console.
- **Pasted script has the wrong hash or line count.** Re-run `paste_to_guest.sh`; it starts with `rm -f /tmp/cosim_test.py`.
- **Stale processes from a previous run.** `pgrep -a 'qemu-system|ids_cosim'`, then `pkill -x ids_cosim; pkill -f qemu-system`, and
  `rm -rf /tmp/cosim` before step 2.
- **Normal (non-co-sim) boot to check the original demo still works:** `cd ~/plx/ids-os && petalinux-boot qemu --kernel` with no `--dtb`.
  The PetaLinux project and its `system.dtb` are not modified by any of the above.

## What you can and cannot claim

Claim: m0's RTL, generated by Vitis HLS 2024.1 (by Janith/P1), was driven by Linux in QEMU through Xilinx's remote-port
co-simulation and matched the Python reference on all 64 canary records.
Do not claim: silicon or timing (the simulated clock is 10 us, not 100 MHz; P1's Vivado implementation report is not checked here), anything about models
m1 to m5, `fpga_regs.py` or the daemon's FPGA backend (not run; the test talks to `/dev/mem` directly).
